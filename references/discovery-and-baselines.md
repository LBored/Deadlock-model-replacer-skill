# 资源发现、环境和基线

## 先识别什么

- 用户显示名可能与内部名称不同。通过当前游戏资源表、角色定义和模型依赖确认目标，不凭音译猜覆盖路径。
- 保存原始包目录、目标二进制资源、提取工具版本与源哈希。模型图还包括 skeleton、动画图/外部动画、材质、贴图、挂点、物理、bodygroup、LOD、面部 morph、UI 特殊模型和道具。
- 按“角色身体”“嵌入身体的道具”“独立武器”“投掷物/召唤物”记录各自归属。资源同属一个文件不意味着它们都应被替换。
- 提取授权所需最小资源集。先用包列表搜索，不全盘枚举，也不先解出整款游戏。
- 原生文件与 glTF/FBX/DMX 等中间文件同时留存。中间格式能看到网格不代表完整恢复了原游戏语义。

## 工具与格式探测

记录可执行文件路径、版本/提交、插件版本、Python 版本和运行命令。调用 `--help` 或检查实际插件操作符后写命令；不要将旧教程参数当成当前 API。Python 依赖需要隔离时创建专用环境，不升级 Blender 的 Python 去迁就无关工具。

定位用户机器已有工具优先。新工具从维护者渠道取得并记录哈希；确认支持目标游戏构建，而不仅是同一引擎名称。对非 Source 2 项目，查清官方 Mod SDK 或社区加载器要求的标识符、骨架匹配、材质序列化、打包/签名以及加载规则；没有验证这些就不开始全量生产。无法完成导入/加载的小例子，应记录兼容阻塞，而非产出外观正确但游戏不能读的包。

启动前检查工作目录以及 TEMP/TMP、插件配置、Blender 用户目录、下载缓存的实际落点，遵守当前用户指定目录。软件安装路径可只读，不要求移动所有现有程序。含非 ASCII 路径导致旧工具失败时，用经验证的独立兼容目录，保持原工具目录结构；不要向全局环境混入不同版本 DLL。

## 版本连续性

基线是明确选中的包哈希和源工程检查点，不是 `current.blend`。开始修复前记录基线包资源清单；每版保存补丁范围、构建命令、源文件、日志和证据。A/B 试验各用独立 stage/输出包，禁止 B 覆盖 A 的唯一源。

若用户只加头像或语音，直接提取已接受模型包合并，不重新编译模型。若只修一个模型字段，则验证该字段以外的结构保持一致；二进制序列化可能改变整块字节时，明确哪些是语义比较、哪些是真正字节相同。

游戏更新后比较源资源哈希与依赖。引用改变时重新提取目标并复核兼容性；不能只改版本文字或文件大小断言来绕过失败。已接受外观保持为参照，新构建留在候选分支。
